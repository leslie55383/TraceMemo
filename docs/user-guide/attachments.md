# 附件正文：Docling 本地解析（本分支功能）

这一版支持主动选择群聊中的 PDF、Word（`.docx`）、Excel（`.xlsx`），在本机提取正文、建立关键词索引，并把已解析的正文交给群聊日报总结。扫描版 PDF 使用本地 RapidOCR。旧版 `.doc`、`.xls` 暂不支持；转换后需要以新格式文件消息重新发送，再从这条新消息解析，不能把另一种格式的本地文件挂到旧消息上。

## 使用

1. 在微信里下载原附件，打开 TraceMemo「档案」中的对应文件消息。
2. 展开消息下方的「附件正文」。首次使用点击「准备本地解析环境」；需要安装 [uv](https://docs.astral.sh/uv/getting-started/installation/)，并能联网下载 Python、依赖和模型。Windows 使用独立 Python 3.12 环境与 CPU 推理，不需要 GPU。
3. 点击「选择本地附件并解析」，在系统文件选择器中选中**这条消息对应的原文件**。文件名不同会再次要求核对；同名也需要自行确认，程序不会猜测本地多个同名文件的对应关系。
4. 出现「正文已加入搜索和日报」后，在「问问微信」按正文中的关键词查询。证据标为「附件正文命中」，保留文件名、PDF 页码 / Excel 工作表 / Word 段落位置，可跳回原文件消息。
   也可直接询问“项目群最近那份 PDF 写了什么”。精确文件消息、搜索结果的消息上下文、会话概览中选中的文件消息，都会只读已有、仍有效的本地正文，不会触发新的解析或下载。
5. 生成日报时，在「纳入的消息类型」勾选「文件」。手动日报默认仍只勾选文本。自动化和 Agent 日报也支持 `messageTypes: ["file"]`；已有规则保持原先选择，新建规则的全选类型包括文件。

日报的记录说明会显示“附件正文 X/Y 份”，指所选 PDF / DOCX / XLSX 文件消息中已解析且仍有效的数量。未解析、解析失败、文件失效的正文不会被猜测或自动补入；其他文件类型仅有文件消息元数据。不会因解析出更多段落而增加聊天消息数。

## 数据与边界

- 解析过程禁止联网；环境准备步骤才下载依赖和模型。Docling 不向作者或模型服务上传附件。
- 正文索引是当前电脑上的明文 SQLite 文件，按微信账号隔离，位于应用数据目录 `attachment-text/<账号哈希>/documents.sqlite`。不要把该目录提交到 Git 或随意分享。
- **使用远程模型进行问答、生成日报时，检索命中的摘录或已纳入日报的正文会发送给你配置的模型服务。** 本地解析不代表后续 AI 总结也在本地；隐私要求高时请配置本地文字模型。
- 首次解析要主动选择本地文件；后台日报只读已有正文，不会自动扫描磁盘、解析新附件或下载微信文件。正文仅用于关键词检索与日报输入，不改写微信数据库，也不包含在普通聊天导出中。
- 附件证据仍指向原文件消息。Word 的段落标记来自解析顺序，没有可保证的排版页码。Excel 不执行宏或公式计算，只读取文档解析结果；表格、合并单元格、低清扫描件仍需核对原件。
- 这不是所有历史附件的完整索引。关键词检索返回有限的匹配摘录；零命中不能证明未解析附件里没有该内容。精确读取、上下文和概览会补充已选文件的正文节选，原始文件消息文本与正文保持分开。

## 指定文件问答的阅读范围

精确消息读取和消息上下文中的 `attachmentText` 是派生正文，`text` 仍是原始文件消息的文字。`attachmentTextState` 区分已读到正文（`indexed`）、没有可用正文（`not_available`，包括未解析或文件失效）、不支持格式（`unsupported`）和本次预算耗尽（`budget_exceeded`）。这些状态不能被解释成“附件没有内容”。

一次查询最多读取 200 条文件消息，每份最多提供正文前 6,000 字符，合计最多 24,000 字符；消息上下文优先给锚点文件分配预算。`attachmentTextCoverage` 给出正文总字符数、本次包含数和 `truncated`。截断时会明确标为节选，并要求回答说明阅读范围；可按关键词另行提问查找后文，或在日报中勾选文件，使用原有的长记录分段总结。会话概览只补充被选中的代表消息，不能用它宣称所有附件已被读取。

这些读取同时验证会话、原消息身份、时间戳和当前账号，避免数据库重建后相同本地消息编号引用旧附件。外部 Agent 通过已有授权的 Local Query API 读取文件消息时，也会收到这些节选与覆盖状态；远程模型仍遵循上面的数据发送边界。

## 更新、取消与清理

本地文件大小或修改时间改变、文件被移动/删除、解析器版本改变后，该份索引会标为失效，并退出搜索和日报输入。用「重新选择并解析」更新；仍有效且文件不变时复用现有结果。文件指纹以大小和修改时间判断，若外部程序刻意保留这两项，需先删除正文索引再解析。

解析可取消。写入采用事务，失败不会写入半份附件；重新解析失败时保留上次成功索引（原文件失效时旧正文仍不会参与检索）。可用「删除正文索引」单独删除，也可到「设置 → 缓存清理 → 附件正文索引」清理所有账号；“清理全部”也包含它。原附件不删除，Docling 环境和模型保留。

解析/删除后，再次提问会重新检索，避免沿用变更前的答案。含附件正文的答案也会在再次提问时重新检查文件有效性。已有问答历史、生成的日报以及已经发送给模型的内容不随单份正文索引删除；这些历史内容需另行清理。

限制：单文件 30 MB、PDF 最多 500 页、Office 解压后最多 150 MB；单文件正文最多 100 万字符 / 1500 段，超限会报错而非静默截断。一次日报最多读取 300 条附件消息，合计正文最多 100 万字符，长记录还受现有分段与超时上限约束。大文件请缩小范围或拆分处理。

## 开发与验证

主进程通过固定 Python bridge 和 JSON stdin/stdout 调用 Docling，渲染进程只能提供原消息引用，不能指定任意读取路径。消息来源由已连接的聊天数据库重新核对，本地文件由原生文件选择器确认。正文派生结果单独存储，不修改聊天源库。

固定版本：Docling `2.142.0`、ONNX Runtime `1.31.0`。环境准备使用 uv 的独立 venv。高级配置可通过 `WXE_DOCLING_PYTHON` 指定已有解析环境、通过 `WXE_UV_EXECUTABLE` 指定 uv；自备环境也需要上述版本。

```powershell
# 仅测试临时生成的文件和假账号，不接触真实聊天或模型 API。
python -m unittest discover -s tests/python -p test_attachment_documents.py -v

# 使用已准备的独立环境，额外验证真正的 PDF / DOCX / XLSX / 扫描 PDF 转换。
$env:TM_DOCLING_TEST_REAL = '1'
$env:TM_DOCLING_MODELS = '<应用数据目录>\docling\models'
$env:HF_HUB_OFFLINE = '1'
$env:TRANSFORMERS_OFFLINE = '1'
& '<应用数据目录>\docling\venv\Scripts\python.exe' -m unittest discover -s tests/python -p test_attachment_documents.py -v

# 额外验证 Electron 主进程服务所用的真实子进程协议。
$env:TM_DOCLING_PYTHON = '<应用数据目录>\docling\venv\Scripts\python.exe'
pnpm exec vitest run --config vitest.integration.config.ts tests/integration/attachment-docling.test.ts
```
